# 0.26.8: mail to a session that has ended finds its role or says it cannot (hub 0.26.8, plugin unchanged)

Effects first: one added column, converted in place; no client breaks.

- **Peer mail to a session that has ended no longer lands in the machine's own mailbox, where 74 % of it expired unread.** It goes to the role the session held when it ended (non-main roles first, the one held longest; its main seat last), and the sender's result says "session X has ended: sent to role:<project>/<role> instead".
- **Privacy guard:** the redirect happens only when the role is now held by the same person (a vacant role is no target). Otherwise nothing is delivered; the sender is told the session has ended and its role is held by someone else, without naming who.
- **A session with no role cannot be written to:** the recipient comes back in `not_sent` ("has ended and held no role; nobody would read it. Address a role instead"); when it was the only recipient, `send` fails with that reason.
- The hub's own notices (an answer to an ask, subscription and deadline notices) are unchanged and still reach the asker's agent mailbox.
- Schema: `sessions.roles_at_end` records the roles at the end. Sessions that ended earlier use their role release events.

Security fixes in the same release (independent review, 2026-11-16): mail to an ended session is redirected only to a role in the message's own project or a linked one, and only to a role held by the same person now (a vacant role is no longer a target; the sender is told it is vacant and which role to address). The texts do not name a session the reader may not see ("a session of <human>"). `sessions.roles_at_end` is NULL for a session that ended before 0.26.8, so only those use release events, and only those after their last start. Also a wall that was open before: `claim_role` no longer lets one person take another's main seat (`main.<name>`), vacant or not.
