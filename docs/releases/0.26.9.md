# 0.26.9: a reply delivered to your session from another project can be opened (hub 0.26.9, plugin unchanged)

Effects first: no schema change; no client breaks.

- **Bug:** a session that wrote to a role open to the whole hub got the reply's summary but `thread` said "no message
  N for you", so the body could not be read. `thread` admitted a reader outside the message's project only through a
  role it holds, not through its own session.
- Now `thread` shows any reader exactly the messages of the conversation that it sent or received (its session, the
  roles it holds in projects it is still in, its agent's mailbox within its own projects), as documented. The rest of
  the thread stays hidden, and a message it neither sent nor received answers like one that does not exist.

Security review of this change (same release, not yet deployed): `thread` had dropped the scope check for agent readers,
so a session could read its agent's own messages from a project it was not working in (with other people's ack notes),
and a token or revived session could keep reading a project its person had been removed from. Now, for a reader outside
the message's project, the agent's mailbox and its sender key are no way in: a conversation opens only if the reader sent
a message in it from inside its own scope (its session's project or a linked one), or it reached a role the reader holds
now. The case this release was made for still works. Also: removing a person from a project now closes their waiting
mail of that project as `withdrawn`, so neither the agent nor a revived session is handed it; and in `thread` receipts a
role a redirect chose, in a project you are not in (and not linked to), reads "a role of <person>'s", as `send` says;
a role you addressed yourself keeps its name.
